# 리팩토링

**기존 동작을 변경하지 않는 범위**에서 코드 구조를 개선한다. 가독성, 재사용성, 유지보수성, 타입 안정성을 높이는 방향으로만 진행하며, `.cursor/rules`의 팀 컨벤션과 기존 아키텍처를 준수한다.

> 목표: 동작은 그대로 두고, 코드 품질과 구조만 개선한다.

## 원칙 (필수)

- **동작 보존**: 리팩토링 후에도 외부에서 보이는 동작(API, UI, 이벤트 결과)이 이전과 동일해야 한다. 기능 추가·삭제·동작 변경은 하지 않는다.
- **최소 변경**: 필요한 부분만 수정한다. 불필요한 대규모 리팩토링은 하지 않는다.
- **주석 보존**: 기존에 존재하던 주석은 삭제하지 않는다. 내용이 틀렸거나 모호한 경우에만 수정·보완한다.

## 사용 시나리오

1. "이 컴포넌트 가독성만 좀 정리해줘"처럼 **특정 파일/컴포넌트**를 다듬고 싶을 때
2. "이 로직 재사용 가능하게 분리해줘"처럼 **훅·유틸 추출**이 필요할 때
3. "타입 좁히기/제네릭 정리해줘"처럼 **타입 안정성**만 개선하고 싶을 때

## 금지 사항

- **기능·동작 변경**: 새 기능 추가, 버그 수정, API 스펙 변경, UI 동작 변경
- **불필요한 대규모 수정**: 한 번에 여러 피처/페이지를 건드리거나, "전체 정리" 식의 광범위한 변경
- **컨벤션 위반**: rules/architecture에 없는 새 레이어·폴더 구조 도입, design-system 대신 직접 구현, `any` 남발

## 실행 흐름

### . 범위와 목표 확인

1. 사용자가 **리팩토링 대상**(파일/폴더/훅 이름)과 **원하는 방향**(가독성, 재사용성, 타입 등)을 파악한다.
2. 관련 규칙을 확인한다.

### 2. 현재 동작 파악

1. 대상 코드의 **입력( props, 파라미터, 쿼리/스토어)**과 **출력(렌더 결과, 부수 효과, 반환값)**을 정리한다.
2. 이 코드를 사용하는 **호출처**를 확인해, 리팩토링 후에도 인터페이스(이름·시그니처·동작)가 호환되는지 기준을 세운다.

### 3. 개선 방향 결정

다음 중 **요청된 것과 컨벤션에 맞는 것만** 적용한다.

| 목표            | 허용되는 작업 예시                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------ |
| **가독성**      | 긴 함수/컴포넌트 분할, early return으로 중첩 축소, 의미 있는 변수/함수명 정리, 매직 넘버/문자열 상수화 |
| **재사용성**    | 반복 로직을 custom hook·유틸 함수로 추출, 공통 UI는 `common/` 또는 design-system 컴포넌트로 사용       |
| **유지보수성**  | 단일 책임에 맞게 파일/함수 분리, 복잡한 조건을 명확한 함수/상수로 분리                                 |
| **타입 안정성** | `any` 제거, 제네릭·union 타입 정리, 불필요한 타입 단언 최소화                                          |

- **파일/폴더 이동**이 필요하면 `architecture.mdc`의 경로 규칙을 따른다.
- **컴포넌트 분리** 시 atoms / molecules / organisms 역할을 지키고, 비즈니스 로직은 훅으로 분리한다.

### 4. 수정 수행

1. **한 번에 작은 단위**로 수정한다. (예: 한 파일 내부 정리 → 필요 시 훅/유틸 추출 → import 경로 정리)
2. **동작 보존**을 위해:
    - props·함수 시그니처·export 이름을 바꿀 때는 모든 **참조처**를 함께 수정한다.
    - 파일 이동 시 **import 경로**와 re-export(barrel)를 갱신한다.

### 5. 검증 체크리스트

- [ ] 기존 동작이 바뀌지 않았는가? (기능·UI·API 호출 결과 동일)
- [ ] 리팩토링 범위에 해당하는 기존 테스트가 통과하는가?
- [ ] 리팩토링 후 eslint/tsc가 모두 통과하는가?
    - 수정한 파일에 한해 새로 발생한 경고/에러는 가능하면 함께 제거한다. (예: `consistent-return`, 사용되지 않는 변수 등)

## 출력 시 사용자에게 전달할 내용

- **변경 요약**: 어떤 파일/함수/타입을 어떻게 바꿨는지 짧게 나열
- **동작**: "기능·동작은 변경하지 않았습니다" 명시
- **규칙 준수**: 참고한 rule/architecture 항목을 필요 시 언급 (예: "비즈니스 로직을 Feature 훅으로 분리(architecture.mdc)")

## 요약

- **입력**: 리팩토링 대상(파일/컴포넌트/훅) + 개선 방향(가독성, 재사용성, 유지보수성, 타입)
- **동작**: 기존 동작을 유지한 채, rules·architecture·project-patterns에 맞게 구조와 코드 품질만 개선
- **효과**: 팀 컨벤션과 아키텍처를 지키면서 가독성·재사용성·유지보수성·타입 안정성이 높아진 코드
